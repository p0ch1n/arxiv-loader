CRITICAL  發現 #1：低確信度訊號在無人值守下被自動放行並實際下單（本次再現一次，共2檔）

6187（08-28）與 2472（08-31）的聚合訊號確信度分別只有 41% 與 33%（皆低於 60% 的人工複核門檻），系統正確觸發了 human_review_required，但在沒有 --checkpoint 的批次模式下都只印出一行 WARNING 然後照樣下單：

01:34:13WARNING Human review triggered for 6187 — reasons: [conviction=0.41 < 0.60]
01:34:21Portfolio decision: BUY 6187 qty=10.00 → Simulated fill: BUY 6187 @ 1365.6825
00:01:03WARNING Human review triggered for 2472 — reasons: [conviction=0.33 < 0.60]
00:01:05Portfolio decision: BUY 2472 qty=10.00 → Simulated fill: BUY 2472 @ 232.6162

兩筆交易都是在沒有任何人核准的情況下真的下了單。有意思的對照組是 2330：同樣是 37% 低信心、同樣自動放行複核，但投資組合經理因為「已有既有部位」而選擇不加碼（見發現#6）——代表低信心自動放行這個洞，只有在「開新倉」情境下才會直接變成一筆交易，管理既有部位時多一層保護。

建議：在 graph/edges.py 的 should_approve_risk 中，當 human_review_required=True 且未啟用 checkpoint 時，預設應該降級為 HOLD 並跳過下單，而不是靜默放行；若要允許批次模式下單，應該要求明確的 --auto-approve-low-conviction 旗標，讓「自動核准低信心交易」變成一個需要使用者主動選擇的行為，而非目前的隱性預設。

CRITICAL  發現 #2：長時間網路/LLM 呼叫掛起，無逾時保護，拖垮整個批次（08-31 追蹤更新：問題未再現）

08-28 那次掃描期間，觀察到 3 次獨立的長時間掛起事件，都發生在「看起來已建立連線、但遲遲沒有回應」的狀態，CPU 幾乎零使用率（代表是在等待網路，而非在運算）：

GEV特徵計算完成 23:56:04 → Sage ML 完成 00:47:03（間隔 51 分鐘，Sage 內部計時器卻只顯示 93 秒）
3131 #1研究備忘錄產出 01:34 → 卡在分析師 LLM 呼叫，2 小時後仍無進展（CPU time 全程未增加），最終手動 kill
3131 #2重啟後又在下一階段卡住 近 50 分鐘，再次手動 kill

根因：用 curl 直接測試 Yahoo Finance 端點，回應是 HTTP 429（Too Many Requests）——整晚對 12 檔標的反覆呼叫 yfinance，最終把這台機器的 IP 給 Yahoo 限流了。yfinance 函式庫內部的重試/退避機制會靜默等待，沒有任何逾時、沒有任何 log 輸出，導致整個 LangGraph 流程看起來像「卡死」。

08-31 追蹤更新：間隔 3 天後，改用「單檔逐一執行、無 log 進展就直接 kill 換下一檔」的操作性緩解策略，重跑 3131/2472/2330，三檔全部在 50~90 秒內乾淨完成，完全沒有再遇到掛起。這支持了「Yahoo 429 是 IP 層級、有時間窗口會自動解除」的假設，但也代表目前完全沒有程式層級的修復——下次若在短時間內重複掃描同一批標的，很可能會再次觸發限流並卡住。

建議（仍未實作，維持原建議）： (a) 在 data/ingestion/sources/yfinance_source.py 加上明確的 request timeout 與有上限的重試次數； (b) 跨標的的批次掃描層級加入節流/快取，同一天同一標的的資料只抓一次； (c) 把 QuestDB 實際啟動起來作為快取層（本次日誌仍顯示 QuestDB unavailable...，代表快取層完全沒發揮作用）； (d) core/llm.py 的 complete()/complete_json() 也應加上 request timeout + 有限重試。

MEDIUM  發現 #3：TWStockSource 對 TPEx 官方端點的逾時設定形同虛設

3131 的籌碼面資料擷取時，log 顯示：HTTPSConnectionPool(host='www.tpex.org.tw'...): Read timed out. (read timeout=15)——但從前一行 log 到這行錯誤，實際經過了超過 6 分鐘，遠超過設定的 15 秒逾時。這代表程式碼裡雖然設定了逾時，但外層可能還有重試邏輯把多次 15 秒逾時疊加成好幾分鐘，且中途完全沒有輸出任何「正在重試」的 log。

建議：在 twstock_source.py 的重試迴圈中，每次重試前印出一行 INFO log（例如「第 N 次重試 tpex.org.tw，將於 X 秒後...」），讓使用者至少能從 log 判斷「這是在重試」而非「卡死了」。
